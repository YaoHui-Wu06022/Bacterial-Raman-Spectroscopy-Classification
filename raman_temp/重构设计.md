# 拉曼光谱分类项目重构设计记录
## 当前实施项：独立推理

### 目标与边界

- 推理必须只依赖正式包 `raman_temp/`，不能导入 `raman/`。
- 保留实验根级联与单个 `run_*` 两种模型选择方式；目标层级仍由显式参数给出。
- 输入预处理复用 `data/InputPreprocessor` 的强度数组接口。读取 `.arc_data`、波数轴过滤和长度校验属于数据层，不写入预测器。
- 推理核心只产生类别概率；文件夹遍历、真值前缀匹配、文本报告、跳过迁移样本和绘图均位于其外层。
- 不在本阶段实现统一顶层 CLI、配置编辑入口或评估指标汇总；但必须迁入推理读取既有 YAML 配置快照所需的最小能力。

### 子包与依赖方向

```text
core/experiment_reader.py  -> 实验根、run、配置快照和层级元数据读取
data/spectrum_reader.py    -> .arc_data 文本、波数轴、有效强度数组
inference/model_runtime.py -> 懒加载模型、run 选择和父类模型缓存
inference/predictor.py     -> 单条输入、单文件和级联 top-k 预测
inference/directory.py     -> 文件夹与谱文件遍历、预测记录收集
inference/report.py        -> 逐文件报告、文件夹汇总和 used_runs.json
inference/plots.py         -> 显式请求时的光谱对照图
inference/independent.py   -> 独立推理编排
```

依赖只能从 `inference/` 指向 `core/`、`data/`、`modeling/` 和 `spectra/`；`core/`、`data/`、`modeling/` 不反向导入 `inference/`。层级标签规范和 logits 遮罩继续由 `core/hierarchy.py` 统一提供。

### 保留的行为与产物

- 单个 run 入口：结果写入该 `run_*` 下的 `test_result/`。
- 实验级联入口：结果写入 `<实验目录>/<目标层级>/test_result/`。
- 每次结果保留 `used_runs.json`、`summary.txt`，每个测试菌文件夹保留 `<文件夹>_file.txt`。
- 文件夹名称可选地映射为预期标签，输出逐谱正确数、投票结果和文件夹正确性；关闭评估时只输出预测汇总。
- `skip_transferred` 仍可依据 manifest 跳过已迁入训练集的谱文件，但它只影响目录编排，不进入模型运行时。
- 训练均值光谱对照图仍为显式选项；默认推理不产生图像。

### 验收

1. 从 `raman` 与 `raman_temp` 分别加载同一已训练 run，比较同一测试谱的 top-k 标签和概率。
2. 覆盖实验级联、全局单 run 与父类单 run 三种模型选择方式。
3. 从 `dataset/测试菌/raw` 抽取一个种的完整子文件夹执行目录推理，比较候选、汇总和输出结构。
4. 检查新包无 `raman` 或临时包导入；函数与变量命名符合既定规则。

> 状态：训练数据索引、数据视图和输入预处理边界已完成；训练规格、运行上下文、优化器拆分和 workflow 按本文分批实施。本文是后续重构的设计基线和决策日志；在目录、导入路径、配置或运行入口发生改变前，必须先更新本文并经用户审核。

## 1. 重构目标与边界

### 目标

- 在不改变现有训练、审核、评估、独立推理和分析行为的前提下，降低模块之间的耦合。
- 让目录边界直接表达职责：数据与审核、模型与训练、实验运行时、评估与推理、可解释分析、共享工具。
- 统一配置、路径、实验产物和层级路由的依赖方向，减少跨包回调与重复入口。
- 将现有根目录脚本和分散命令重构为统一入口；不保留旧脚本、旧命令或旧 import 路径的长期兼容层。
- 在迁移期间明确替换入口与迁移说明；配置字段、实验目录结构、checkpoint 和层级元数据的兼容策略须逐项确认。
- 包名切换后，`raman/` 只作行为基线；所有后续功能实现均写入 `raman_temp/`。
- 将随包存放的数据资源移出 Python 包目录；参考波数文件固定为仓库根级 `dataset/Stanforddataset/reference_wavenumbers.npy`。
- 新包的重要函数应有适量中文注释，说明职责、关键输入输出、关键约束或副作用，便于后续检索与维护。
- 降低模块依赖熵：依赖方向清晰、职责唯一、无循环依赖；不将现有实现视为唯一正确设计。

### 非目标

- 不以“顺便优化”为名修改算法、默认超参数、数据处理顺序或结果格式。
- 不删除原理说明、审核规则或已有实验兼容逻辑。
- 不在设计未确认前进行大规模文件移动。
- 不直接修改、移动或删除现有 `raman_temp/` 中的功能代码；它只用于行为对照和迁移验收。

### 架构依赖规则

```text
cli → workflow → 领域包（data / audit / training / evaluation / inference / analysis）
领域包 → core / spectra / common
extensions → 领域包 / core / spectra
```

- `core`、`spectra`、`common` 不反向依赖任何领域包；`spectra` 只依赖数值与科学计算库。
- `data` 不依赖 `audit`、模型或训练；`audit` 可调用 `data` 的 I/O 与构建服务，但不反向注入审核逻辑。
- `modeling` 不依赖训练、评估、推理或分析；`training` 不依赖评估、推理或分析。
- `cli` 只解析参数和调用 workflow；workflow 不包含数值算法、文件格式解析或绘图实现。
- 每迁移一个包，增加依赖检查，禁止新循环和跨层反向 import。

### 设计修正规则

- 现有实现仅作为行为证据；发现职责混杂、重复功能、隐式路径、危险写入或不必要复杂度时，应提出修正方案。
- 不改变业务语义的简化可直接实施，并在 `重构日志.md` 说明。
- 会改变算法、数据处理顺序、输出格式、配置语义或实验结果的修正，必须先记录“问题、方案、影响、验证方式”，经确认后实施。
- 验收以明确的行为契约为准；需要修正的行为不以字节级等价作为唯一目标，而应增加对应的预期测试。

## 3. 已识别的设计议题

1. **入口层过薄但分散**：根目录 `train.py`、`evaluate.py`、`infer_test.py`、`analyze.py` 是脚本入口；应收敛为 `raman_temp/__main__.py` 与 `raman_temp/cli/`，旧入口不做长期兼容。
2. **数据构建与审核的边界**：`data` 处理可再生训练/测试集，`audit` 修改原始库并输出审核报告。两者应共享纯光谱处理函数，但不应相互承担目录编排职责。
3. **实验上下文的职责过重风险**：配置读取、实验目录解析、run 选择和结果目录解析集中在 `experiment.py`；需要拆分“不可变元数据读取”和“运行期路径决策”，但保留统一门面。
4. **微调包存在两套路径**：`raman_temp/raman_fine_tuning/` 与根目录 `raman_fine_tuning/` 并存。重构后应隔离为 `raman_temp/extensions/stanford_finetune/`，只作为 Stanford 预训练之后可能启用的扩展；现有两条路径只用于对照，不在旧包内删除或修正。
5. **共享工具包需要收口**：`tool/` 是正确的基础依赖方向，但应避免继续添加训练、审核或推理专属逻辑；后续需要按“纯函数 / 文件系统 / 领域公共模型”分组。

## 5. 拟定迁移原则

1. 先建立测试/冒烟验证，再移动实现；数据处理迁移以每次从 `dataset/alldata/init/` 随机抽样后的产物对比为准。
2. 迁移前先建立“旧函数 → 新职责模块 → 验证方式”的映射；优先复用已迁移的功能，不为相近职责重复创建函数。
3. 先抽取无副作用、无目录写入的纯函数，再处理流程编排。
4. 每个迁移阶段都提供明确的新入口；临时转发仅用于迁移过程，重构完成前必须删除，且不放新逻辑。
5. 所有涉及 `output/`、`dataset/`、`delete/`、`test_result/` 的改动必须做产物路径对比。
6. 配置字段、YAML 读取、模型 checkpoint 键和层级元数据格式在第一阶段保持不变。
7. 新增或迁移的功能代码只写入 `raman_temp/`；旧 `raman_temp/` 仅作行为基线，不在其中修正问题或实施迁移。
8. Stanford 参考波数统一从项目根级固定路径 `dataset/Stanforddataset/reference_wavenumbers.npy` 读取，不再使用相对于 Python 包或当前工作目录的路径。
9. 重要函数必须配有适量中文注释；注释解释职责、关键数据约定、算法边界或文件写入副作用，不逐行复述代码。

### 阶段验收基线

- **数据处理层**：每次验收从 `dataset/alldata/init/` 随机抽取样本；同一次验收中，旧包与 `raman_temp/` 使用同一批样本，记录随机种子、相对路径和数量，比较谱数据、标签及预期产物是否一致。
- **模型相关迁移**：使用已有实验 `output/GN/20260802_231209_88%/` 的 checkpoint 进行独立推理，确认模型构建、权重加载、层级路由和输出结果正常；必要时与旧包结果对比。
- **训练相关迁移**：本地仅有 Python 3.10 与 CPU PyTorch 环境，因此只进行可完成一个极小批次的训练、验证、保存和恢复的冒烟测试，不将其视为性能或精度回归。

### 分阶段迁移顺序

1. `core/paths.py`（项目根目录与固定参考资源路径解析）和 `spectra/`。
2. 数据处理层：`data/`，并完成随机抽样的产物对比。
3. `audit/` 及其流程编排，并完成对应样本和报告产物对比。
4. 仅在前三步成功后，开始 `modeling/`、`training/`、`evaluation/`、`inference/` 和 `analysis/` 的迁移与模型基线验证。

### 审核包目标边界

```text
audit/
├─ config.py       # AuditConfig：阈值、锚点、白名单与路径约定
├─ io.py           # 审核阶段的严格原始谱读取
├─ preprocess.py   # Stage2、Stage3 共用的训练一致预处理
├─ records.py      # RawRecord、SimilarityRecord 等审核记录
├─ raw_quality.py  # Stage1 原始质量检查与候选判定
├─ shift.py        # 自动/人工平移与 delta 记录
├─ similarity.py   # Stage2、Stage3 近邻相似性审核
├─ reports.py      # 三阶段 CSV、delta 日志与测试菌清单
├─ plots.py        # 前缀图与平移图
├─ test_sync.py    # 测试菌运行池复制、回写与重建编排
├─ workspace.py    # 运行池 candidate 移动与提交前路径管理
├─ workflow.py     # clean 全流程编排
└─ cli.py          # 命令入口
```

- `clean` 在 `audit_runs/<run>/work/` 的运行数据池中依次完成测试菌同步、Stage1、自动平移、Stage2、Stage3、测试菌回写和副本重建；不自动生成审核图。
- 每个 Stage 判定 candidate 后立即从运行数据池移入对应的 `work/delete/stage*/`，并写入提交计划。只有全部审核阶段成功后，才按提交计划更新真实 `init/`、`delete/` 与 delta，并回写测试菌、重建副本；失败时保留运行目录和错误记录，真实数据不变。
- `manual-shift` 仅处理指定数据集的 `init/`，不触发训练集构建；若处理测试菌 `init/`，同时平移 `alldata/init/` 中对应的 `*t` 文件夹，并同步两侧 `delta.txt`。两侧已有同名 delta 且数值不一致时必须报错，不覆盖任一记录。
- 自动平移的锚点范围、真菌双峰规则、特殊文件夹累计平移与大平移白名单统一由 `AuditConfig` 提供；工作流不通过读取其他数据集目录决定算法分支。
- 绘图仅通过独立命令执行，保留前缀图与平移图。
- 配对复核不进入目标包。
- 属级复核不作为独立功能迁移；属内、跨属近邻关系由 Stage2、Stage3 的审核记录覆盖。
- 审核验证从 `dataset/alldata/raw` 与 `dataset/测试菌/raw` 复制一个完整种及其对应测试菌目录到临时数据集执行；比较三个 Stage 的主数据、测试菌 `delete/` 相对路径，不进行全量审核或修改原始数据。

### 训练集 PCA 清洗开关

- `pca_enable` 默认关闭。
- 当 `pca_enable=False` 时，构建 `train/` 不执行 PCA 异常样本筛除，不创建、重置、写入或打印 `pca_log.txt`。
- 当 `pca_enable=True` 时，才创建 PCA 日志并记录被筛除样本；`pca_components`、`pca_center_enable` 和 `pca_outlier_ratio` 是 PCA 专属参数。
- 数据层验收须覆盖开、关两种情形：关闭时确认无 PCA 日志且样本数不因 PCA 改变；开启时确认筛除结果与日志对应。

### 训练数据运行时与增强

- `data/input.py` 负责单条原始强度谱到模型输入张量的确定性链路：归一化、平滑、`d1`、通道堆叠与输入长度检查。
- `data/augmentation.py` 负责仅训练集启用的随机变换：归一化前的分段增益、噪声、轴扰动和基线扰动，以及归一化后的平移、展宽和局部衰减。
- `data/index.py` 提供 `DatasetIndex`，一次扫描训练目录并保存样本路径、层级标签、类别表、父子映射及只读原始强度缓存；它是切分、训练、验证和层级元数据共同使用的结构化数据来源。
- `data/dataset.py` 的 `RamanDataset` 只作为 PyTorch 数据视图：按索引读取 `DatasetIndex` 的强度数据、调用输入构建，并按 `augmentation_enable` 决定是否施加随机增强。训练与验证视图共享同一个 `DatasetIndex`，不重复扫描目录或维护模块级缓存。
- `InputSpec` 保存确定性输入字段；`AugmentationSpec` 单独保存随机增强字段。两者均由完整配置在内存中构建，数据集不长期保留完整配置对象。
- 输入通道只支持原始谱、可选平滑谱和可选一阶导数 `d1`；不提供二阶导数 `d2` 通道。

### Stanford 扩展配置边界

Stanford 预训练与迁移微调应完全位于 `extensions/stanford_finetune/`，不写入常规 profile 映射。根据现有两套微调实现，配置分为以下两类：

- **预训练配置**：Stanford 数据位置与导入状态、固定参考波数位置、输入网格模式 `stanford_transfer`、归一化 `minmax`、Stanford 专属数据增强与 batch size、训练层级、训练轮次/早停、随机种子、可选损失覆盖和预训练输出目录。
- **迁移配置**：来源预训练 run 与层级、目标常规 profile 及其训练层级/父类范围、学习率、输出目录、是否重建目标 `train/`，以及显式列出可训练模块的冻结策略。
- **自动校验项**：来源与目标的波数范围、点数、输入网格、归一化、滤波、网络结构和参考轴必须兼容；目标数据始终按 Stanford 共享网格构建。
- **避免重复配置**：迁移时模型结构和固定输入处理参数以来源 run 的已记录配置为准，不在 `transfer.yaml` 中重复填写；扩展只接受目标数据与训练策略相关字段，并在执行前校验兼容性。

建议在扩展包内将 `config.py` 用于配置模型和校验，并将可编辑的 YAML 放入 `configs/pretrain.yaml` 与 `configs/transfer.yaml`；两者均不参与 `core/profiles.py` 的普通 profile 映射。

| 当前函数 | 目标模块 | 处理方式 | 验证方式 |
| --- | --- | --- | --- |

### 包、文件与命令命名

- 包名使用名词：`training`、`evaluation`、`inference`；不使用含糊的 `tool`、`utils` 作为业务包名。
- 编排名使用职责词：`runner.py` 表示一次完整执行，`service.py` 表示可复用应用服务，`workflow.py` 表示多步骤流程，`report.py` 表示结果格式化与落盘。
- 一级命令使用领域名或稳定动词：`train`、`evaluate`、`infer`、`analyze`、`audit`、`data`。
- 同包内不重复领域名：`training/loop.py`，不使用 `training/training_loop.py`；`analysis/embedding.py`，不使用 `analysis/analysis_embedding.py`。

### 函数、变量与类命名

- 代码标识符一律使用英文 `snake_case`；中文只用于注释和文档。
- 函数动词必须表达行为：`read_*` 读取文本，`load_*` 读取结构化数据，`parse_*` 解析，`build_*` 构建新产物，`preprocess_*` 处理光谱，`write_*` 写单文件，`save_*` 保存结果，`publish_*` 发布临时产物，`resolve_*` 解析路径或配置。
- 布尔函数和变量只使用 `is_*` 或 `*_enable`；布尔开关以 `*_enable` 命名。
- 私有函数同样写完整职责，不使用 `_helper()`、`_process()` 等泛名。
- 返回路径、目录和掩码的函数分别以 `_path`、`_dir`、`_mask` 结尾。
- 变量名保持简短且能表达数据角色，不拼接重复的领域词；配置和数据类使用单数名词 PascalCase，如 `DataBuildConfig`、`PackedArcDataset`。
- 应用代码避免为项目模块或函数使用 `import as`；`numpy as np` 等稳定的第三方库惯例可保留。等价测试可使用别名区分对比对象。

### 训练运行时命名约定

- `DatasetIndex` 表示一次扫描后形成的样本、标签、层级和强度缓存索引；`RamanDataset` 仅表示该索引的 PyTorch 数据视图。
- `ExperimentContext` 与 `RunContext` 只持有目录、日志句柄等短生命周期外部资源；不引入 `Manager`、`Service`、`Helper` 一类泛名对象。
- 训练范围与任务分别固定为 `TrainScope`、`TrainTask`；训练入口请求为 `TrainRequest`；单任务产物和结果固定为 `TrainArtifacts`、`TrainResult`。`TrainingState` 仅用于跨 epoch 可恢复状态。
- 训练构建函数固定为 `build_loader`、`build_optimizer`、`build_scheduler`、`build_train_artifacts`；`build_loader` 接收完整 `LoaderSpec`，不通过 `is_train` 区分训练与验证。
- checkpoint 模块使用 `save_checkpoint`、`restore_checkpoint`、`remove_checkpoint`；验证模块使用 `evaluate_loader`；数值诊断写入函数使用 `write_nonfinite_diagnostic`。
- 输入构建使用 `build_model_input`、`preprocess_intensity`；随机增强使用 `build_augmentation_spec`、`augment_raw_spectrum`、`augment_normalized_spectrum`。
- 公共名称使用完整单词 `validation`，不使用 `val`；局部变量可使用 `val_loader`、`val_indices`。`meta` 只用于稳定文件格式名 `hierarchy_meta`，函数仍使用 `load_hierarchy_meta`、`save_hierarchy_meta`、`build_hierarchy_entry`。

### `data` 命令组的职责

`data` 是离线数据产物的唯一入口，负责把已审核的原始数据构造成 `train/`、`test/` 和相应审图/统计产物；它不执行原始库审核或平移，后者始终属于 `audit`。

命令形式为：

```text
python -m raman_temp data build train <profile>
python -m raman_temp data build test <profile>
python -m raman_temp data pack <profile>
python -m raman_temp data unpack <profile>
python -m raman_temp data count <profile>
python -m raman_temp data plot <profile>
```

其中 `data build train` 是当前“从 `init/` 构建 `train/`”的规范化替代，`data build test` 是当前“从 `init_test/` 构建 `test/`”的规范化替代。

- 优化仍采用 AdamW 与余弦退火；可训练参数分为 stem `0.6×`、主体 `1.0×`、分类头 `1.1×` 三组学习率。
- Align、SupCon、Focal、EMA、SE 统计、早停、checkpoint、数值诊断和 train/val 切分继续保留。
- 全局层训练、按父类训练、单子类跳过记录、指定父类训练和恢复训练继续保留。
- 实验的配置快照、日志、模型、SE sidecar、checkpoint、split 文件和 `hierarchy_meta.json` 的外部文件名与目录含义保持可读取。

## 9. 训练与数据运行时目标方案（已确认，分批实施）

### 9.1 总体调用关系

```text
cli/train
  → training.workflow.run_training
      → core.config：解析冻结规格
      → core.run_context：实验根、run、快照与日志
      → data.index：一次扫描并建立 DatasetIndex
      → training.split：切分、范围解析、TrainTask 枚举
      → data.dataset：训练/验证数据视图
      → modeling.factory：按 ModelSpec 构建模型
      → training.loop：单个 TrainTask 的 epoch 循环
      → core.hierarchy_meta：汇总并写入层级模型索引
```

`workflow.py` 是唯一了解“本次训练有多少层级任务”的位置；`loop.py` 只了解“当前这个模型如何训练”。`core` 只管理共享规格、路径和元数据，不调用训练算法；`data` 不导入模型或训练模块。

### 9.2 配置、规格与运行上下文

完整配置对象只存在于 CLI 和 workflow 的边界，用来写入实验快照；任何数据集、模型、循环或损失函数都不能长期保存它，也不能回写它。解析后的对象均为冻结 dataclass。

| 对象 | 所在位置 | 只包含 | 不包含 |
| --- | --- | --- | --- |
| `InputSpec` | `core/input_spec.py` | 点数、归一化、平滑、`d1`、窗口和步长 | 路径、随机增强、模型参数 |
| `TrainingSpec` | `training/spec.py` | 训练轮数、早停、切分、loader、优化器和损失子规格 | 数据路径、run 路径、模型实例 |
| `ExecutionSpec` | `training/spec.py` | 设备选择、随机种子、确定性、AMP、恢复和 checkpoint 周期 | 训练超参数、目录扫描结果 |
| `AugmentationSpec` | `data/augmentation.py` | 各随机变换的启用概率与幅度 | 模型、路径、train/val 索引 |
| `ModelSpec` | `modeling/spec.py` | 网络结构与分类头构建字段 | 数据集、训练循环状态 |

`TrainingSpec` 使用 `LoaderSpec`、`OptimizerSpec`、`LossSpec` 三个冻结子规格表达各自的参数域，避免一个平铺对象同时承载切分、优化、辅助损失和早停字段。`core/input_spec.py`、`training/spec.py` 和 `modeling/spec.py` 分别是输入、训练/执行、模型字段到规格的唯一适配位置。固定的行为常量必须在其所属模块以具名常量表达，不能在规格构建函数中散落字面量。

`core/run_context.py` 提供两个短生命周期对象：

- `ExperimentContext`：实验根目录、共享配置快照和 split 路径；负责打开或恢复一个实验，不创建实验根级日志。
- `RunContext`：单个模型槽位的 run 目录、日志句柄和本次配置快照；负责暴露产物路径并在结束时关闭文件。

`RunContext` 不保存模型、数据集、optimizer 或 epoch 状态；`training.workflow` 根据其路径构建 `TrainArtifacts`。训练循环不创建目录、不写配置快照，也不直接编辑 `hierarchy_meta.json`。`core/hierarchy_meta.py` 只读写层级元数据和模型条目，不打开训练日志或构建模型。

运行上下文只接收 workflow 已解析的实验目录、模型槽位和 run 目录，不生成时间戳、不选择 profile，也不修改完整配置对象。`open_experiment_context(...)` 创建或校验共享快照；`resolve_run_dir(...)` 只计算或校验目标 `run_*` 目录；`open_run_context(...)` 创建该 run 的日志、配置快照和固定产物路径。写入 `resolved_config.yaml` 时，由完整配置导出字典叠加本次的 `output_dir`、`experiment_dir` 与 `run_dir`，不回写原配置。单个 run 只保留 `logs/run.log` 和 `logs/config.txt`，避免同一 run 内重复维护模型专属日志。

### 9.3 数据运行时：索引、视图与输入构建

```text
训练目录
  → DatasetIndex
      ├─ 样本路径、数值层级标签、类别名称、父子映射
      └─ 建立索引时一次性读入并缓存只读原始强度
  → RamanDataset(index, input_spec, augmentation_spec, augmentation_enable)
      ├─ 训练视图：augmentation_enable=True
      └─ 验证视图：augmentation_enable=False
```

`DatasetIndex` 是数据目录的一次性结构化描述，负责目录扫描、稳定类别编码、`get_split_key()`、层级查询，并在建立索引时一次性读取全部原始强度形成只读缓存。它不创建模型输入，不持有 PyTorch 设备，不知道训练轮数。缓存是 `DatasetIndex` 的实例状态，不使用模块级全局字典；一个训练工作流只创建一个索引实例，训练与验证视图共同使用它。

`RamanDataset` 不再重新扫描目录、生成类别表或编码 collate 后的层级名称。它的单样本返回值固定为“模型输入、数值层级标签、样本路径”三项；层级名称和父子映射需要时由 `DatasetIndex` 查询。这样训练和验证循环只处理数值标签，不再在每个 batch 将字符串层级名称再次编码。

`data/input.py` 只提供强度数组到输入张量的确定性函数，负责归一化、平滑、`d1`、通道堆叠和长度校验。`InputPreprocessor` 面向推理和分析时的单条强度数组预处理，只接收强度数组；`.arc_data` 的读取始终归属 `data/io.py`，避免输入模块同时承担文件读取职责。随机变换全部位于 `data/augmentation.py`：归一化前变换先作用于原始强度，归一化后变换作用于确定性谱；验证、评估、推理和分析均不传入增强规格。

### 9.4 训练任务与单任务循环

`TrainScope` 仅表达用户请求的层级、父类和筛选范围。切分完成后，workflow 将它解析为一个或多个 `TrainTask`；`TrainTask` 是单模型训练所需的不可变语义对象，包含：层级名与索引、可见类别 ID、局部标签映射、train/val 索引、父类 ID（如适用）和模型标签。它不包含路径、模型实例、完整配置、optimizer 或日志函数。

- 全局层任务使用该层全部类别，局部标签映射为空。
- 父类子模型任务只保留目标父类的样本和子类 ID，局部标签映射将全局标签转换为该模型的分类头标签。
- 某父类只有一个子类时不创建 run；workflow 直接生成 `status="skipped_single_child"` 的层级元数据条目。
- 指定父类训练只枚举该父类对应的 `TrainTask`；恢复训练必须指向该任务的模型槽位内既有 run。

`training/loop.py` 的公开函数为 `run_train_loop(...)`，只接收模型、训练/验证 loader 对、`TrainTask`、`TrainSpec`、`RuntimeSpec`、`TrainArtifacts` 和显式日志写入函数。它不接收 `TrainContext`，不读取完整配置，也不判断应该训练哪些父类。为支持隔离的微调扩展，它额外接受可选 `apply_training_mode` 回调；常规训练不传入，扩展模块在每个 epoch 设置冻结模块的训练状态，循环不导入任何扩展代码。

训练包内部再按下列职责划分：

```text
training/
├─ losses.py       # 张量损失、类别权重与辅助损失权重
├─ split.py        # TrainScope、切分持久化、范围过滤与 TrainTask 枚举
├─ optimizer.py    # 三组参数、AdamW 与余弦调度器构建
├─ checkpoint.py   # 训练状态、恢复、清理 checkpoint
├─ validation.py   # 单任务验证、预测与指标汇总
├─ se_stats.py     # SE hook 统计与 sidecar 保存
├─ diagnostics.py  # 首个数值异常的摘要与缩进 JSON 写入
├─ loop.py         # 一个 TrainTask 的 epoch、早停和最佳权重决策
└─ workflow.py     # 训练入口、任务枚举、run 管理与元数据汇总
```

`TrainArtifacts` 仅保存单个 run 的模型、SE sidecar、checkpoint 和诊断文件路径；日志句柄属于 `RunContext`，由 workflow 显式传入写入函数。`TrainResult` 只返回最佳 epoch、最佳分数和已经写入的产物路径。这样数据、运行目录和训练状态没有可变共享对象。

### 9.5 workflow、实验产物与恢复规则

`TrainRequest` 定义在 `training/workflow.py`，包含已经解析的完整配置、可选 `resume_run_dir`，以及仅供隔离微调扩展使用的可选 `initialize_model(model, task)`、`apply_training_mode(model)` 回调；常规训练不传回调。训练层级、父类和筛选条件继续从配置读取。请求进入 workflow 后配置只读，不在任何步骤回写。`training.workflow.run_training(request)` 的固定顺序为：

1. 读取请求和完整配置，解析 profile、数据目录与冻结规格；不修改输入配置对象。
2. 打开 `ExperimentContext`，创建或校验共享配置快照，并载入或生成一次全局 train/val 切分。
3. 构建唯一 `DatasetIndex`，解析 `TrainScope`、应用筛选条件并枚举 `TrainTask`。
4. 对每个非跳过任务打开对应 `RunContext`，写入 run 配置快照，构建训练/验证数据视图、loader、模型与 `TrainArtifacts`，再调用 `run_train_loop(...)`。
5. 将 `TrainResult` 或单子类跳过记录转换为层级模型条目，最后由 `core/hierarchy_meta.py` 一次汇总写入 `hierarchy_meta.json`。

每个训练条目继续写入相对实验根的 `run_dir`、`model_path`、`config_path`、`resolved_config_path`、`log_path`、split 文件名及其哈希；`core/hierarchy_meta.py` 合并当前条目与已有层级条目及 run 历史，再一次性保存。这样后续训练一个新层级或父类不会丢失已完成模型的索引。

单个 run 继续使用当前外部目录语义：run 内保存 `model_config.yaml`、`resolved_config.yaml`、`*_model.pt`、`*_se_stats.pt`、`*_checkpoint.pt` 与 `logs/run.log`、`logs/config.txt`、`logs/*_numerical_diagnostic.json`；实验根保存共享配置、split 文件和 `hierarchy_meta.json`。模型、SE sidecar 与 checkpoint 文件名保持不变；诊断只写首个异常 batch 的单个缩进 JSON 对象。

恢复训练只允许使用目标 `TrainTask` 槽位内的既有 `run_*` 目录；workflow 按该 run 的既有状态追加日志并恢复。除槽位定位和当前已有的实验共享配置约束外，本阶段不增加模型配置或 split 的额外比对规则；恢复不新建并行 run，不改变训练任务范围，不重建 split。

### 9.6 依赖边界与命名审查

```text
cli → training.workflow → core / data / modeling / training
training.loop → core / modeling / training
data → core / spectra
core → common
```

- `training/optimizer.py` 是三组学习率的唯一位置；`loop.py` 不再按参数名分组。
- `training/diagnostics.py` 是数值诊断文件的唯一位置；`loop.py` 只在发现异常时调用它。
- `data/index.py` 是层级编码与原始强度缓存的唯一位置；`split.py` 不复制类别映射。
- `core/hierarchy.py` 只保留层级键、映射校验和张量掩码；元数据文件 I/O 归入 `core/hierarchy_meta.py`。
- 函数名称遵循第 7 节：创建对象使用 `build_*`，读取结构化数据使用 `load_*`，解析路径或范围使用 `resolve_*`，单文件写入使用 `write_*`，保存组合产物使用 `save_*`。项目模块不使用 `import as`。

### 9.7 验收与替换顺序

1. 为 `DatasetIndex` 建立目录扫描、类别编码、父子映射、缓存共享和 train/val 视图测试；从 `dataset/alldata/init/` 随机抽取样本，在关闭增强时比对输入张量和标签。
2. 对 `InputSpec`、`AugmentationSpec`、`TrainingSpec`、`ExecutionSpec` 建立纯规格测试，确认完整配置不会被修改；固定随机种子验证训练增强结果可复现。
3. 对 `TrainTask` 建立全局任务、父类子任务、单子类跳过和指定父类筛选测试；固定索引对比 split 文件与局部标签映射。
4. 对 `optimizer.py` 验证参数无遗漏且学习率为 `0.6×/1.0×/1.1×`；对 checkpoint 验证模型、optimizer、scheduler、RNG 与 AMP GradScaler 恢复。
5. 在 Python 3.10 CPU PyTorch 环境运行极小的全局任务和父类子任务，覆盖训练、验证、最佳模型、SE sidecar、checkpoint、恢复与 `hierarchy_meta.json` 写入。
6. 使用 `output/GN/20260802_231209_88%/` 的 checkpoint 做模型加载与小样本推理检查；运行依赖检查和命名检查，确认没有新增反向 import、重复领域函数或项目代码 `import as`。
7. 上述检查完成后，才将实际改动、验证结果和命名/依赖审查写入根级 `重构日志.md`，并更新第 6、7 节的实施状态。

实施顺序固定为：先替换数据索引与输入视图，再替换冻结规格与 run 上下文，然后拆分优化器和诊断，最后实现 workflow 与全流程冒烟。每一步必须先完成对应测试，后一步不得依赖未经验证的草案。

## 10. modeling 迁移方案（已落实）

本节只定义模型层的目标边界与验收契约；在确认前不继续调整模型实现。

### 10.1 目标文件与职责

```text
modeling/
├─ spec.py          # ModelSpec、配置解析与结构前置校验
├─ layers.py        # 激活、卷积块、SE、残差瓶颈、位置编码
├─ heads.py         # CosineClassifier 等分类头
├─ classifier.py    # RamanClassifier1D，只负责网络组装和前向
└─ factory.py       # build_model：模型构建的唯一应用入口
```

- `layers.py` 和 `heads.py` 不读取配置文件、训练状态、路径或 checkpoint。
- `classifier.py` 只接收 `ModelSpec`，不读取宽泛配置对象，不依赖训练、评估、推理或分析包。
- `factory.py` 是训练、评估、推理和扩展模块构建网络的唯一入口：`build_model(num_classes, model_spec)`。
- checkpoint 路径解析、run 选择、`torch.load`、类别路由和设备选择不属于 `modeling/`；它们在后续 `core` / `inference` / `training` 中实现。
- backbone 只保留 `cnn` 与 `direct` 两种类型；不保留 identity 或独立下采样语义。

### 10.2 完整配置与领域规格

每个可运行实验仍保留完整的 `resolved_config.yaml` 快照。完整快照是复现和审计依据，不因字段数量多而裁剪；其体积不是问题，问题是模块直接消费无关字段。

配置层从完整快照派生领域规格：

```text
resolved_config.yaml
├─ InputSpec       # 波数轴、预处理、归一化和输入通道
├─ ModelSpec       # 网络拓扑、编码器、池化和分类头
├─ TrainingSpec    # 优化器、损失、增强、切分、早停
└─ ExecutionSpec   # 设备、断点恢复和 checkpoint 周期
```

- 首阶段只在内存中从完整配置构造这些规格，不额外保存多份 YAML，避免产生重复配置源。
- `core/input_spec.py` 从 `InputConfig` 构造 `InputSpec`；`modeling/spec.py` 和 `training/spec.py` 分别构造 `ModelSpec`、`TrainingSpec`、`ExecutionSpec`，`modeling` 不识别任何特定配置类。
- `ModelSpec` 是冻结的数据类，只保留会影响参数形状、模块树或前向计算的字段。学习率、损失、数据增强、UMAP、路径、设备和断点恢复不进入其中。
- `classifier.py` 不提供任意配置字段读取方法；所有字段转换、默认值和名称映射集中在 `build_model_spec`。

### 10.3 ModelSpec 与前置校验

`spec.py` 提供 `ModelSpec`、`build_model_spec(model_config, input_spec)` 与 `validate_model_spec(model_spec)`。

`ModelSpec` 包含：输入通道、backbone 类型、CNN block 类型、ResNeXt 宽度与基数、SE 开关与 reduction、stem 核尺寸、投影维度、序列编码器参数、池化类型、余弦分类头开关与 scale、激活斜率。

`backbone_type` 只允许两种路径：

- `cnn`：多尺度 CNN 主干提取并下采样，再进入 Transformer、LSTM 或空 Encoder；
- `direct`：仅经 `input_proj` 对齐通道，完整波数轴直接进入 Transformer、LSTM 或空 Encoder。

不保留单独的下采样路径，不设置 `identity_pool_kernel`；`direct` 不改变谱轴长度。

构建前统一验证以下条件：

- `transformer_dim` 能被 `transformer_nhead` 整除；
- ResNeXt 中间通道满足 `cardinality` 分组卷积要求；
- `reduction`、通道数、层数、池化核和分类数均为有效正数；
- `backbone_type`、`cnn_block_type`、`encoder_type`、`pooling_type` 都属于支持集合；其中 `encoder_type` 保留 `none`，用于纯 CNN 对比；

`validate_model_spec(model_spec)` 只执行上述结构校验。输入长度属于 `InputSpec`，由 `validate_model_input(model_spec, input_spec)` 在训练和推理构建后调用，检查 CNN pooling 或完整谱轴直连后的输入能完成前向。

配置中的既有 `*_use` 字段保留；`ModelSpec` 与模型内部布尔字段统一使用 `*_enable`。字段转换只发生在 `build_model_spec`，不在网络构建方法中分散读取。

### 10.4 模型构建与参数键契约

`build_model(num_classes, model_spec)` 负责先校验规格，再构建 `RamanClassifier1D`。分类器构建完成后不保留完整 config，只保存前向所需的标量与模块。

构建期临时对象不作为模型长期属性保留，包括配置来源、block 参数字典、激活层工厂、stem 通道分配和 stage 通道传递状态。前向期只保留参与路径判断的 `cnn_backbone_enable`、`transformer_enable`、`lstm_enable`、`pooling_type`、`cosine_head_enable`，以及实际参与计算的 PyTorch 模块。

为使已有权重原生严格加载，以下模块名称和嵌套层级冻结：

```text
stem_branches
layer1 / layer2 / layer3 / layer4
proj
input_proj
pos_encoder / transformer / lstm
att_pool
head
```

层名称和参数键是模型结构契约，不通过重命名映射、键转换或临时转发加载权重。`_make_layer` 改为显式接收输入通道并返回输出通道，消除构建过程中的隐式通道状态，但不改变上述模块树。

当前验收基线 `output/GN/20260802_231209_88%/level_1/run_20260802_231210/` 使用 `backbone_type: cnn`；其中记录的 `identity_pool_kernel` 不参与该网络的模块构建与权重加载。后续 `direct` 模型按完整谱轴训练和保存，不接受下采样配置。

### 10.5 checkpoint 最小加载契约

一个可推理模型的最小信息为：

```text
state_dict + ModelSpec + InputSpec + class_names
```

- `state_dict` 只保存参数和 buffer；不混入优化器、路径或训练临时状态。
- `ModelSpec` 决定网络结构，`InputSpec` 决定输入预处理与张量形状，`class_names` 决定 logits 的类别含义。
- 完整 `resolved_config.yaml` 继续随 run 保存，用于追溯和完整复现；加载模型时不要求读取其中的训练或运行期字段。
- 本次不引入键名转换、隐藏兼容分支或自动修补缺失参数；不符合结构契约的 checkpoint 应直接报错。

### 10.6 前向与特征提取接口

模型公开前向结果固定为两种：

- 默认返回 `logits`；
- 显式使用 `return_embedding_enable=True` 时返回 `(logits, embedding)`。

`embedding` 指池化后的样本级特征。IG、Grad-CAM、UMAP、损失计算和层级类别遮罩均在模型外部调用该接口或命名模块，不写入分类器内部。

### 10.7 验收顺序

1. 层、分类头和完整分类器的 `state_dict` 键逐项一致；参考权重可 `strict=True` 加载。
2. 固定随机种子、固定输入下，对比 logits 和 embedding 数值。
3. 使用 `output/GN/20260802_231209_88%/level_1_model.pt` 与同 run 的结构配置、类别清单执行严格加载和一次 CPU 前向。
4. 覆盖 CNN + Transformer + attention pooling、CNN + 无序列编码 + statistic pooling、direct + LSTM + cosine head 三种组合。
5. 验收后检查 `modeling` 的依赖仅指向 PyTorch、标准库和本包；不反向导入 `training`、`evaluation`、`inference`、`analysis` 或配置实现。

## 11. 配置层重设计（已落实）

### 11.1 目标与入口

- `raman_temp/core/config.py` 是唯一的常规可编辑配置源；用户只在此处调整默认参数。
- 配置源继续是 Python 的 `Config` 对象；`shared_config.yaml`、`model_config.yaml` 和 `resolved_config.yaml` 只作为实验产物快照，不新增手写 YAML 入口。
- 配置按领域语义组织，不按 YAML 写入位置组织；配置对象不读取数据目录、不构建波数轴、不解析 profile，也不保存运行目录。
- 删除扁平属性代理。新包代码显式访问 `config.input`、`config.model`、`config.training` 等分组，不通过 `config.xxx` 隐藏字段归属。

### 11.2 配置分组

```text
Config
├─ dataset: DatasetConfig
├─ input: InputConfig
├─ model: ModelConfig
├─ training: TrainingConfig
└─ execution: ExecutionConfig

AnalysisConfig  # 分析迁移时再加入 Config
```

- `DatasetConfig`：`profile_id` 及常规数据集选择信息；具体路径由 `data/profiles.py` 解析。
- `InputConfig`：波数范围、重采样点数、坏段、归一化、`smooth_use`、`d1_use` 和 SG 窗口。它定义训练、验证、推理共同的输入契约。
- `ModelConfig`：backbone、CNN block、SE、编码器、池化、分类头和 stem 的结构参数。
- `TrainingConfig`：训练切分、DataLoader、增强、优化器、调度器、损失和早停参数。
- `ExecutionConfig`：随机种子、设备、AMP、确定性设置和 checkpoint 周期。
- `AnalysisConfig` 暂不创建空对象；分析迁移时再加入 UMAP 等参数，避免没有实际字段的抽象。

`TrainScope`、恢复目录、实验目录、run 目录和输出目录不属于 `Config`。训练范围进入 `TrainRequest`，路径由 `ExperimentContext` 和 `RunContext` 解析。

### 11.3 依赖与派生规格

```text
core/config.py       -> 仅标准库与配置数据类
data/profiles.py     -> DatasetConfig.profile_id 到路径的映射
data/config.py       -> 离线构建专属算法参数
core/input_spec.py   <- InputConfig
modeling/spec.py     <- ModelConfig + InputSpec
training/spec.py     <- TrainingConfig + ExecutionConfig
```

- `core/config.py` 不导入 `data`、`spectra`、`modeling`、`training` 或 `analysis`。
- `InputConfig` 是波数轴与坏段的唯一配置来源；`data/config.py` 只保留基线、宇宙射线、PCA 和样本阈值等离线构建参数，不再向核心配置提供默认值。
- 每个领域包只消耗自己的冻结规格：`InputSpec`、`ModelSpec`、`TrainingSpec`、`ExecutionSpec`。规格中的布尔字段使用 `*_enable`；可编辑配置继续使用 `*_use`。
- `build_input_spec`、`build_model_spec`、`build_training_spec` 和 `build_execution_spec` 分别完成字段转换与局部校验，不在模型、训练循环或推理代码中分散读取配置字段。

### 11.4 快照规则

- `shared_config.yaml`：`DatasetConfig` 与 `InputConfig` 的扁平字段。
- `model_config.yaml`：`ModelConfig`、`TrainingConfig` 与本次 `TrainRequest` 的任务范围快照。
- `resolved_config.yaml`：上述字段、`ExecutionConfig` 与解析后的路径信息；继续保持扁平字段结构，保证既有实验结果可读取。
- 快照读取先恢复分组配置，再构建对应 Spec；路径信息只用于定位，不回写到可编辑配置对象。

### 11.5 实施结果与验收

- `core/config.py` 已收敛为仅依赖标准库的不可变配置数据类；`DatasetConfig`、`InputConfig`、`ModelConfig`、`TrainingConfig`、`ExecutionConfig` 由 `Config` 显式聚合，默认项按参数域写有中文注释。
- `core/input_spec.py`、`modeling/spec.py` 与 `training/spec.py` 分别从输入、模型、训练/执行配置构建冻结规格；模型和训练循环不再读取完整配置。
- `core/config_file.py` 只读写 YAML 快照并校验共享字段；`core/experiment_reader.py` 返回只读 `RunSnapshot`，路径和任务范围保持为元数据。
- `TrainRequest` 显式持有训练层级、父类与筛选范围、实验目录、run 名称和恢复目录；`Config` 不保存这些短生命周期状态。
- `data/config.py` 只保留离线构建算法参数；波数轴和坏段由 `InputConfig` 统一提供。审核配置分别持有 `input` 与 `cleaning`，避免输入轴和基线算法混用。
- 已完成共享/模型/完整快照、checkpoint 严格加载、CPU 训练冒烟、审核和模型等价测试；当前 `tests/` 为 51 项通过。

### 11.6 `config_file.py` 的职责修缮

`core/config_file.py` 只处理配置快照文件本身，不构建运行上下文，不解析实验目录，也不修改配置对象。

保留的职责：

- `read_yaml_dict`、`write_yaml_dict`：单个 YAML 文件的原子读写。
- `save_shared_config`、`save_model_config`、`save_resolved_config`：将调用方已准备好的快照字段写入对应文件。
- `assert_shared_compatible`：比较同一实验根的共享字段。
- YAML 可序列化值转换与三个快照文件名常量。

`core/experiment_reader.py` 负责读取实验根与 run 快照、调用 `build_config`，并返回包含 `Config`、实验根和 run 路径的只读读取结果。`experiment_dir`、`run_dir` 只属于 `ExperimentContext`、`RunContext` 或读取结果，不写回 `Config`。

`resolved_config.yaml` 仍保存路径、任务范围与执行字段，便于复现和排查；这些字段在读取时作为元数据返回，不成为可编辑配置字段。
